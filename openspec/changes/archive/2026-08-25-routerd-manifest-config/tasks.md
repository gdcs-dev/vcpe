- [x] 1.1 Confirm the exact JSON field casing/shape `routerctl apply` expects by inspecting `serde`/`schemars` derives for `ConfigDocument`, `RawResource`, `ObjectMeta`, `ApiVersion`, and the `Interface`/`Bridge`/`WanPolicy` specs in `services/routerd/source/routerd/crates/{resource-types,l2/l2-types,wan/wan-types}` (check for `#[serde(rename_all = ...)]` on any of them). - [x] 1.3 Confirm `ResourceRef`'s shape (how an `Interface` is referenced from `Bridge.members`/`WanPolicy.interface_ref`) in `resource-types`. - [x] 7.2 Bring up the routerd deployment with the real Podman runtime and confirm `routerctl apply` succeeds against the rendered config inside the running container (validates the section-1 wire-format assumptions against the live binary). Ran `vcpe up --manifest manifests/dev/routerd.yaml` against a real Podman machine. This surfaced and fixed three real, in-scope bugs uncovered only by live execution:
  - The generic `IFACE_*_MAC`/`IFACE_*_DEVICE` rename could collide with the health-publication sidecar's unnamed interface (which has no `IFACE_*` identity) claiming the target device name first; `entrypoint.sh` now displaces any such untracked occupant to a scratch name before the final rename.
  - `ROUTERD_BIN_DIR` defaulted to a stale `/workspace/target/release` path from the old bind-mounted-source Containerfile; the current Containerfile installs the `routerd`/`routerctl` apt package to `/usr/bin`, so the default was corrected.
  - The real `routerd`/`routerctl` CLIs take `--socket-dir <dir>` (deriving per-contract socket filenames themselves), not a single `--socket <file>`; `entrypoint.sh` and `health-probe.sh` were updated to use `ROUTERD_SOCKET_DIR` and poll readiness via `routerctl describe` instead of guessing a socket filename. `health-probe.sh`'s hardcoded `ip link show brlan0` check (another GATEWAY-derived assumption not applicable to routerd's manifest-driven topology) was also removed.
  After those fixes, execution proceeds cleanly through interface rename → `prepare_config` (confirms the rendered `etc/routerd/config.json` artifact is correctly mounted and copied into place) → daemon startup. The daemon then failed on a genuinely separate, out-of-scope gap: the vendored `routerd` binary requires its own `/etc/routerd/deployment.json` **provisioning/composition-root descriptor** (which components/profiles this process runs — see `crates/routerd/src/catalog.rs`'s `Provisioning` type and `crates/routerd/src/provisioning.rs`). This is unrelated to the desired-state `ConfigDocument` this change renders — it's static and identical for every deployment of this binary, so it belongs baked into the image, not manifest-derived. Resolved by adding `services/routerd/container/provisioning/` (deployment.json + components/{config,state-event,capability,operation,intent,l2,l3,dhcp_client,wan}.json + profiles.json + identity.json, adapted from the vendored `scripts/playground.sh` reference) and `COPY`ing it to `/etc/routerd/` in the Containerfile.
  Two further real bugs surfaced once the daemon actually started: `routerctl apply` takes `--file <path>` (not a bare positional argument) — fixed in `entrypoint.sh`; and the rendered `Interface`/`Bridge` specs left `admin_up` as JSON `null` ("track but leave as-is" in the real L2 controller), so the interface never came up and DHCP failed with "Network is down" — fixed by rendering `admin_up: true` on every `Interface`/`Bridge` resource in `routerd.go`.
  **Fully verified end-to-end** against the live Podman deployment: `routerctl status all` inside the running container shows `Interface/eth0`, `WanPolicy/eth0-wan-policy`, `DhcpClient`, `IpAddress`, and `Route` all `Ready`, with a real DHCP lease (`10.7.200.100` from BNG) applied at the kernel level (confirmed via `ip addr`/`ip route` inside the container).

## 8. Manifest consistency: reuse the standard bridge fields

- [x] 8.1 Discovered post-completion: the user edited `manifests/dev/routerd.yaml` to declare LAN bridging the same way `gateway`/`example.yaml` do — `interfaces[].bridge: brlan0` + a top-level `services[].bridges: [{name, ipv4, dhcpStart, dhcpEnd}]` — instead of routerd's own `config.bridges: [{name, members}]`. The bridge silently wasn't created: the routerd renderer only ever read `config.bridges`, so a manifest written in the (more common, pre-existing) generic style produced no `Bridge` resource at all.
- [x] 8.2 Removed the routerd-specific `config.bridges`/`BridgeConfig` schema and `validateBridges` entirely. `routerd.Config` is now an empty struct. The renderer derives bridge groupings directly from each resolved interface's `Bridge` field (already populated by the planner from `interfaces[].bridge`), matching `gateway`/`bng` exactly — one manifest vocabulary for bridging across every service type. This also removes the whole "member references an undeclared role" error class: grouping by resolved interfaces can never reference a role that doesn't exist.
- [x] 8.3 Fixed a second bug this surfaced: with two unbridged DHCP interfaces (`wan` + `cm`, mirroring gateway's `erouter0`/`wan0`), both previously got `WanPolicy{priority: 1}`, and the real `routerd` daemon logged a route conflict ("equal-authority contenders excluded") instead of installing either default route. `WanPolicy.priority` is now derived from the existing `defaultRoute` interface field: the `defaultRoute: true` interface gets `priority: 1`; other unbridged interfaces get strictly increasing priorities in role-name order.
- [x] 8.4 Updated `routerd_golden_test.go` for the new mechanism (bridge grouping via `Interface.Bridge`, empty `Config`, unknown-config-field rejection) and added `TestRouterdMultipleUnbridgedInterfacesGetDistinctPriority` covering the two-uplink priority fix. Updated the `routerd-manifest-config` spec and `design.md` decisions 2/3 to describe the final mechanism. `go build ./...` and `go test ./internal/types/routerd/...` pass.
- [x] 8.5 Re-validated end-to-end against the live Podman deployment with the user's gateway-consistent manifest (`interfaces[].bridge` + `services[].bridges[]`, both `wan` and `cm` unbridged with `defaultRoute` only on `wan`): `routerctl status all` shows `Bridge/brlan0` (members `eth0`–`eth3`) and both `WanPolicy`/`DhcpClient`/`IpAddress`/`Route` sets `Ready`, with `ip route show` confirming distinct metrics (100 for the `defaultRoute` interface, 200 for the other) and no conflict warnings in the daemon log.
