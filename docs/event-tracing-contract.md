# Event Traceability Contract

This document defines the minimum integration required to make a defensible
end-to-end claim about an event emitted by an application. It applies to
applications written in any language and using any event protocol.

A successful trace must support this claim:

> The selected application emitted one identified event through its normal
> production event client, the configured routing system selected a delivery
> path, and the intended receiver accepted the resulting authenticated
> delivery.

A trace is not application performance telemetry, arbitrary event injection,
or a guarantee that every production event will be delivered.

## Trace Boundaries

A complete trace has four independently observable boundaries:

```text
application -> event client -> routing system -> receiver
      source acceptance       route selection    accepted delivery
```

Each boundary requires evidence owned by the component that directly observes
it. A control plane may assemble evidence, but it must not invent an event,
replace a component's credentials, or infer delivery from connectivity alone.

| Boundary | Required claim | Evidence owner |
| --- | --- | --- |
| Application to event client | The selected application client accepted one trace event. | Application or its in-process client integration |
| Event client to routing system | The normal transport accepted or forwarded the event. | Client or transport |
| Routing system | A route was selected for the trace identity. | Router, broker, or dispatcher |
| Receiver | The intended receiver accepted an authenticated delivery for the same identity. | Receiver |

The receiver receipt is the only completion proof. Source acceptance and route
selection alone are not proof of delivery.

## Required Trace Identity

Every active trace needs a new opaque correlation ID generated by a trusted
orchestrator or the source application. The ID must be carried unchanged in
the event and made available to the receiver.

A suitable default is 32 cryptographically random bytes encoded as lowercase
hex. The implementation must:

- generate a new ID for every trace;
- validate the exact expected syntax and size at every boundary;
- avoid using user, customer, device, hostname, timestamp, or payload data as
  the correlation ID;
- retain it only for a bounded diagnostic lifetime; and
- avoid logging or displaying it unnecessarily.

The trace event needs a reserved, minimal marker that carries the correlation
ID and identifies the diagnostic protocol version. The marker must be distinct
from normal application payload semantics. For example:

```json
{
  "diagnostic": "event-trace/v1",
  "correlationId": "<opaque-id>"
}
```

The exact wire encoding can be JSON, a message header, protobuf metadata, or a
native protocol extension. It must not require arbitrary caller-supplied
payloads, headers, destinations, credentials, or callback URLs.

## Source Application Integration

The strongest trace starts inside the application that normally produces the
class of event being diagnosed.

The source integration must provide a narrow local interface that accepts only:

- a fixed or allowlisted application client name;
- a bounded, allowlisted event kind or destination;
- the exact locally owned device, tenant, or subject identity when applicable;
- the generated correlation ID; and
- explicit permission to emit one diagnostic event.

The source application, library, or adapter must construct the actual event
using its normal client implementation and its existing source identity,
connection, credentials, and protocol configuration. It then reports whether
its normal send or enqueue operation accepted the event.

This integration may be implemented in C, C++, Go, Rust, or another language. The language does not matter; source ownership does.

### Reference Implementation: Gateway AppArmor Simulator

The Gateway [AppArmor simulator](../services/gateway/src/apparmor-simulator/apparmor-simulator.c)
is a concrete C reference implementation of this contract. It is not a
required protocol or language binding; another application should preserve the
same boundaries using its own normal event client.

Its trace path maps to this contract as follows:

| Contract requirement | AppArmor simulator implementation |
| --- | --- |
| Restricted local interface | Creates `/run/apparmor-simulator-diagnostic.sock` as a Unix stream socket with `0600` permissions. |
| Bounded request | Reads at most 512 bytes and strictly parses one JSON object with exactly four fields. |
| Fixed source selection | Requires `clientService` to be exactly `apparmor-simulator`. |
| Local identity ownership | Requires `deviceId` to equal the simulator's `device_id`, derived from the local `erouter0` MAC address. |
| Allowlisted input shape | Accepts only a bounded event destination and a lowercase 64-hex correlation ID. |
| Reserved marker | Builds a minimal `cpe-webpa-callback` payload containing the correlation ID. |
| Normal client path | Constructs a WRP event with the application's normal source and destination convention, then calls `libparodus_send`. |
| Source acceptance evidence | Returns `accepted` only when `libparodus_send` returns zero; otherwise returns `rejected`. |
| Safe operational evidence | Logs the sanitized destination and send result, but not the correlation ID or marker body. |

The important characteristic is that `emit_diagnostic_event()` lives in the
same process that owns the normal libparodus client. Replacing it with a
control-plane sender or a separate sidecar would reduce the claim to that
sender's ability to reach the router; it would no longer prove that the
application client accepted the event.

### Appropriate Local Interfaces

Possible interfaces include:

- a Unix domain socket with restrictive filesystem permissions;
- a loopback-only HTTP endpoint with strict schema validation;
- an authenticated local RPC method;
- an application-owned management API; or
- an in-process diagnostic function exposed through the application's existing
  administration surface.

The interface must be local or otherwise strongly access-controlled. It must
not expose a general-purpose "send arbitrary event" capability.

### Source Acceptance Evidence

A source acceptance result should state only whether the application's normal
client accepted the bounded trace event. It may include a safe status category,
such as `accepted`, `client-offline`, `connection-unavailable`, or
`send-rejected`.

It should not expose credentials, raw payloads, full internal configuration,
or unbounded library errors. A source log may record a sanitized destination
and result code, but must not record opaque correlation IDs or secrets unless
there is an explicit, reviewed operational need.

## Passive Preconditions

Before generating traffic, collect enough passive evidence to rule out obvious
misconfiguration. The exact checks depend on the platform, but commonly
include:

1. The selected application client is registered, online, or otherwise ready.
2. The source can resolve the event service.
3. The source can establish the required transport connection.
4. Source credentials are accepted by the event service.
5. The source identity is registered or authorized.
6. The receiver declares its desired subscription intent.
7. The routing system's authoritative registration matches that intent.
8. The selected event kind and source identity match the registration filters.
9. The registration is current enough to be trusted.

Passive checks do not prove delivery. They establish that the single active
trace will exercise a plausible, intended path instead of producing an
ambiguous failure.

## Routing Observation

A router, broker, or dispatcher may expose a bounded trace lookup keyed only by
the correlation ID. When available, it should report a minimal record such as:

```json
{
  "correlationId": "<opaque-id>",
  "state": "route-selected",
  "observedAt": "2026-08-17T14:00:00Z"
}
```

Record the observation after the system's ordinary matching or sender-selection
logic, not before it. The route lookup must not expose arbitrary message
contents, credentials, receiver URLs, subscription inventories, or unrestricted
router internals.

A routing observation is useful diagnosis evidence but remains weaker than a
receiver receipt. A queued, retried, rejected, or restart-lost event can have a
routing record without successful delivery.

## Receiver Receipt

The receiver must own the final receipt. It records a trace only after normal
delivery authentication and validation have succeeded.

For an HTTP callback receiver, the sequence is typically:

1. Receive the normal callback request.
2. Enforce ordinary method and size limits.
3. Validate the normal signature, token, mTLS identity, or other delivery
   authentication.
4. Strictly parse the reserved trace marker and correlation ID.
5. Confirm the request came through the expected routing path when the
   transport provides that distinction.
6. Store a bounded receipt keyed by the correlation ID.
7. Return the normal success status.

The receipt should retain only:

```json
{
  "correlationId": "<opaque-id>",
  "source": "router",
  "acceptedAt": "2026-08-17T14:00:01Z",
  "status": 204
}
```

Keep receipts in a capped, expiring store. A receiver restart may erase them;
that outcome is `unknown` or `inconclusive`, not evidence that delivery failed.
The receipt API should allow lookup by one validated correlation ID only. It
must not provide enumeration, arbitrary log access, or raw callback bodies.

## Orchestration Sequence

An orchestrator can coordinate the trace without becoming an event sender.
Its responsibility is to select known participants, invoke their bounded
diagnostic interfaces, and merge the evidence.

1. Resolve the fixed source, router-side participant, and receiver from trusted
   deployment state.
2. Discover supported diagnostic capabilities through persisted, local
   endpoints.
3. Collect passive source and receiver-registration evidence.
4. Verify the selected event and source identity match the receiver's
   authoritative filters.
5. Generate one correlation ID.
6. Request one source-owned trace event.
7. Query the bounded router observation, when supported.
8. Poll the receiver's bounded receipt endpoint for a short, fixed interval.
9. Render evidence as `passed`, `failed`, `unknown`, or `skipped`.

The orchestrator must use fixed or persisted endpoints. It must not accept
arbitrary hostnames, ports, URLs, commands, executable paths, credentials, or
raw event messages from the operator.

## Evidence Semantics

Use four states consistently:

| State | Meaning |
| --- | --- |
| `passed` | The owning participant positively validated its boundary. |
| `failed` | The participant observed a definite broken condition. |
| `unknown` | The required evidence could not be safely obtained or validated. |
| `skipped` | A blocking prerequisite failed or was unknown, so this stage was not attempted. |

Do not convert an unavailable receipt into `failed`: it may have expired, been
lost during a restart, or fallen outside the bounded observation window. Mark
it `unknown` unless the receiver or transport provides a definite rejection.

Preserve independent passed evidence even when a later boundary fails. This
makes the first confirmed break actionable without claiming certainty beyond
what the participants observed.

## Safety and Privacy Requirements

An event-trace implementation must:

- require explicit operator consent before sending an event;
- send at most one bounded trace event per invocation;
- use a reserved diagnostic marker, not arbitrary application data;
- keep source credentials, router credentials, and receiver secrets inside
  their owning processes;
- validate all request and response schemas strictly;
- cap request bodies, response bodies, receipt retention, candidate lists,
  polling attempts, and total duration;
- bind diagnostic interfaces to loopback or another authenticated local
  boundary where practical;
- redact secrets, signatures, tokens, raw payloads, and sensitive identifiers
  from diagnostic output; and
- leave ordinary production event processing unchanged.

A direct injection into a router or broker can be a useful lower-level routing
test, but it must be described accurately. It proves only the router-to-receiver
portion of the path and cannot establish application-to-client traceability.

## Implementation Checklist

Before claiming end-to-end traceability, verify that all of the following are
true:

- [ ] The real source application owns the diagnostic emission.
- [ ] The source emits through its normal event client and transport.
- [ ] The active operation accepts only bounded, allowlisted inputs.
- [ ] The trace event includes a fresh opaque correlation ID.
- [ ] The source reports normal-client acceptance or a concrete rejection.
- [ ] Passive prerequisites validate source readiness and receiver selection.
- [ ] The selected event and source identity match authoritative routing
      filters.
- [ ] The routing system can provide a bounded correlation-specific observation,
      or the implementation documents that this evidence is unavailable.
- [ ] The receiver validates normal delivery authentication before recording a
      receipt.
- [ ] The receiver receipt is keyed by the same correlation ID and identifies
      the routed delivery path.
- [ ] Receipts and observations are bounded, expiring, and non-enumerable.
- [ ] Missing evidence is reported as `unknown`, never fabricated as success or
      failure.

## Traceability Levels

The following labels prevent overclaiming:

| Level | What it proves |
| --- | --- |
| Registration validation | The intended subscription and its authoritative registration agree. |
| Router injection | A synthetic event already injected into the router reaches the receiver. |
| Source-owned trace | The real source application's normal client emitted one event that reached the receiver. |
| Production observability | Production events are retained and correlated over time. This is outside the scope of a bounded diagnostic trace. |

Use `source-owned trace` only when the application itself emits through its
normal client and the receiver records a matching authenticated receipt.
